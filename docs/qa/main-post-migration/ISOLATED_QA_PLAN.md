# Separate QA project plan

The main project's reported 047/048 execution does not make it a disposable test environment. Keep main's reader configuration separate from all QA write credentials. Do not point automated signup, assessment, reward, upload or destructive tests at main.

1. The project owner creates a separate Supabase project in the dashboard with an unmistakable QA name. Store its project reference, database password and keys only in private local configuration. Do not overwrite the deployed/main environment files or reuse main's database/service-role credentials. Provisioning the project is a separate owner action; no cloud resources were created by this task.
2. An authorized operator captures a reviewed **schema-only** main snapshot after the manual migration changes. Keep public schema/types/functions/constraints/triggers/policies/grants, the actual migration ledger/checksums, and necessary Storage bucket/policy configuration. Do not export real Auth users, table rows, password hashes, Storage files or mail credentials. Keep Supabase-managed Auth/Storage infrastructure from the new project. Review the snapshot before restoring it into QA.
3. Reconcile the historical TEXT/UUID and missing-column issues in [SCHEMA_BASELINE_REVIEW.md](../SCHEMA_BASELINE_REVIEW.md). The QA baseline should already contain whichever definitions the snapshot establishes for 047/048; **do not blindly rerun either migration**. Validate actual catalog signatures/body fingerprints and the [schema preflight](../ISOLATED_SCHEMA_PREFLIGHT.sql) in QA.
4. Start a separate local API and frontend using the QA project's own configuration. Use [the isolated environment example](../../../scripts/qa-staging.env.example) and the target guards. Main project origins remain denied to fixture writers. Main's `.qa/main-readonly.env` is for verification only and must never become the application's runtime configuration.
5. Create dedicated synthetic Admin, Teacher, Parent and Student Auth accounts plus unrelated Teacher/Parent/Student accounts. The existing gated account provisioner stores credentials only in ignored private files; enable it only after the full QA baseline and target identity are confirmed. Confirm role profiles, teacher grade ranges, two parents' children, section/roster relationships and deliberate unauthorized ownership cases independently. Confirmed fixtures are not email-verification evidence.
6. Seed only synthetic curriculum, module/assessment content, attempts, progress, reward boundaries, messages, schedules, PDFs, assignments and notifications. Record expected counts and ownership in a fixture manifest. Include empty/archived/disabled states and known grade/capacity limits. Back up only disposable QA fixtures before negative tests.
7. Test Auth password login, role landing, account switching, stale requests, refresh/logout/revocation, disabled/archived users and protected routes with real QA tokens. Test direct browser RLS using anon-key clients and each authorized/unrelated identity. Service-role writes are reserved for controlled fixture setup/backend behavior, never used to pretend browser isolation passed.
8. Use a test mail inbox and disposable routable addresses for actual signup confirmation, OTP expiry/reuse/resend, password reset and credential delivery. Configure only dedicated SMTP/provider credentials. Keep the existing main email configuration untouched.
9. Use a dedicated speech-provider account/quota and real microphone/device for Filipino TTS listening and Tagalog speech recognition, including denial/no-speech/interruption/unsupported cases. Mocked provider responses or text transcripts alone do not establish real speech quality.
10. Run cross-role learning/assessment/completion/progress/reward workflows, concurrency and failure rollback, upload/Storage/Realtime, every dashboard control, keyboard/assistive technology, responsive desktop/mobile browsers, and representative load in QA. Destructive tests stay within explicitly disposable fixtures. Record actual outcomes; blocked main checks and unexecuted QA cases remain blocked/not run.

No deployment is part of this plan. Release requires independent main catalog/integrity evidence, a verified compatible backend artifact, completed QA signoff and explicit approval. The current missing reader connection does not justify administrator/service-role substitution or RLS changes.
